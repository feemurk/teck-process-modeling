# Entity Extraction Guide
# templates/entity-extraction.md
#
# This template governs how Claude Code runs the `extract entities for [product-name]`
# command. It produces process-model-ref.md — the scoped entity extract that is the
# foundation for the BEAM workshop.
#
# The scoping decision is a human gate. The agent proposes; the human confirms.
# Do not write process-model-ref.md until the scope is explicitly confirmed.

---

## PURPOSE

`process-model-ref.md` serves two functions:

1. **It is the pre-populated foundation for the BEAM workshop.** The agent reads it
   at workshop start to know what it already knows — so it only asks for what it doesn't.

2. **It is the authoritative scope declaration for the data product.** Every entity in
   this file must be accounted for in `beam-overlay.yaml`. Every entity in `beam-overlay.yaml`
   must originate from this file. The two files are always in 1:1 correspondence.

---

## EXTRACTION PROTOCOL

When `extract entities for [product-name]` is issued:

### Step 1 — Collect scoping inputs

Ask for:
```
Product name:     [Must match the intended teck-data-modeling folder name]
DDVC layer:       curated | contextualized
Product purpose:  [One sentence — what decision does this product enable?]
Pillar(s):        [Which pillar MDs are in scope — can be more than one]
Process areas:    [Which L2 process areas within those pillars]
Sites in scope:   [HVC | QB | ANTAMINA | CDA | RED_DOG — list all]
Primary site:     [The site driving the canonical model]
```

If the stakeholder is uncertain about process areas, help them:
> "Based on your product purpose statement, the most likely process areas are [X, Y, Z].
> Does that match what you have in mind?"

---

### Step 2 — Read the pillar models

Read the Entity Catalog sections of the specified pillar model(s).

For each entity in the catalog, evaluate:

**Include if:**
- Entity type is in scope for the declared DDVC layer:
  - Curated product → Master entities, Reference entities, Transactional entities
    (not Contextualized KPI/metric entities)
  - Contextualized product → All entity types that the curated product will have
    already resolved
- Entity is generated by or participates in the specified process areas
- Entity is at the DDVC layer the product targets (check the `DDVC Layer` column
  in the entity catalog)

**Exclude if:**
- Entity type is `Time-Series` and the product is Curated at event grain (time-series
  entities are Capture layer concerns; their aggregated forms may appear in Contextualized)
- Entity is flagged as `Contextualized` in the DDVC Layer column and the product is Curated
- Entity belongs to a different pillar/domain and is only referenced (not owned) by this
  process area — note the cross-pillar dependency but don't include the entity itself
- Entity is explicitly out of scope per the product purpose statement

---

### Step 3 — Propose the scope

Present the proposed entity list with rationale:

```
PROPOSED ENTITY SCOPE — [product-name]

Pillar(s): [list]
Process areas: [list]
DDVC layer: [curated | contextualized]

INCLUDED ENTITIES ([N]):

  MASTER ENTITIES:
  ┌─────────────────────────────┬──────────────────────────────────────────┐
  │ Entity Name                 │ Rationale for Inclusion                  │
  ├─────────────────────────────┼──────────────────────────────────────────┤
  │ [entity_name]               │ [why — what process area, what role]     │
  └─────────────────────────────┴──────────────────────────────────────────┘

  REFERENCE ENTITIES:
  [same table format]

  TRANSACTIONAL ENTITIES:
  [same table format]

EXCLUDED ENTITIES ([N]):
  [entity_name]: [reason for exclusion]
  [entity_name]: [reason for exclusion]

CROSS-PILLAR DEPENDENCIES (referenced but not owned):
  [entity_name] from [pillar]: [how it is used — FK to it, not modeled here]

Does this scope match your intent?
Any entities to add or remove before I write the file?
```

---

### Step 4 — Handle scope disagreements

**If the stakeholder wants to add an entity not in the process model:**
> "That entity isn't in the process model for [process area]. Can you describe what it
> is in business terms? It may be covered under a different name, or it may be a
> Teck-specific entity that needs to be documented as an extension."
Log it as a `vocabulary_addition` candidate and include it as a custom entity with
`source: teck-specific` in the output file.

**If the stakeholder wants to include a Contextualized entity in a Curated product:**
Flag it directly:
> "[Entity name] is a [KPI / aggregate / metric] — it belongs in the Contextualized layer.
> The Curated product should contain the atomic measures that [entity] is calculated from.
> Shall I identify which atomic entities feed into [entity] instead?"

**If scope is significantly larger than expected (>15 entities for a curated product):**
> "This scope is broad. A Curated product with [N] entities is manageable but will
> take multiple workshop sessions. Shall we prioritise the highest-value entities for
> this workshop and park the rest as a second iteration?"

---

### Step 5 — Write process-model-ref.md

On explicit confirmation of scope, write the file.
